# devflow-agent

AI Software Development Manager — агентна система, що веде життєвий цикл розробки
для одного розробника або малої команди.

**Дві мети однакової ваги: працюючий продукт і розуміння того, як він
влаштований.** Не жертвувати жодною. Не давати готовий код без пояснення — але й
не зупинятись на навчальних прикладах там, де потрібна робоча фіча.

Домен зафіксовано один і він тягнеться крізь усі фази, щоб кожна нова тема
лягала на той самий проєкт.

Поточна позиція, фази й відкриті питання — у `ROADMAP.md`.
Перевірки й потоки даних — у `CHECKLIST.md`.

## Як працювати з користувачем

TypeScript-розробник, код зі строгими типами.

Відповідь: кілька речень + схема або код. Мінімум заголовків і списків. Складну тему
бити на кроки, кожен зі своєю схемою.

Код завжди з розбором, що він робить; «що це за файли» — сигнал сповільнитись,
не претензія. Але фічу доводимо до робочого стану, а не лишаємо прикладом.

Перед новим файлом, рефакторингом чи зовнішньою дією — описати план і дочекатись
«так».

Коміти без трейлерів `Co-Authored-By` і `Claude-Session`; автор
`skipokylas <skipokylas@gmail.com>` заданий локально. Push тільки з дозволу.

## Продукт

Один агент на репозиторій. Пʼять здатностей, у порядку залежності:

1. **Журнал рішень** — `.devflow/DECISIONS.md` у цільовому репо: чому зроблено
   саме так, які інваріанти не ламати, що вже пробували. Версіонується з кодом,
   приходить тим самим PR.
2. **Ведення задач** — опис → підзадачі → картки на борді → виконання. Бракує
   вхідних — пише в чат і продовжує одразу після відповіді.
3. **Верифікація** — ворота за зростанням ціни: typecheck і тести → білд →
   браузер.
4. **Прозорість** — дерево кроків із вартістю, посилання `/trace/<runId>`
   привʼязане до задачі.
5. **Коміти й PR** — гілка на задачу, ніколи не в `main`.

**Агент кодить сам.** Рушій за портом `Executor`: v1 — власний цикл,
Claude Agent SDK — друга реалізація, вмикається за даними.

## Сценарій MVP

Має запрацювати end-to-end:

1. користувач підключає GitHub-репозиторій;
2. надсилає запит на фічу (канонічний приклад: «додати passwordless-авторизацію
   через email magic links»);
3. агент читає репозиторій і документацію;
4. генерує acceptance criteria та план;
5. користувач переглядає й підтверджує план;
6. агент створює GitHub issues без дублікатів;
7. розробник відкриває PR, повʼязаний з issue;
8. агент відстежує статуси рев'ю та CI;
9. повідомляє про впалі перевірки й блокери;
10. після мержу готує release notes;
11. усі дії доступні в аудит-лозі.

## Закриті рішення

Не переглядати без явного запиту користувача.

| Рішення | Чому |
|---|---|
| TypeScript, не Python | основна мова користувача; мета — зрозуміти архітектуру, а не боротись із мовою |
| Голий `@anthropic-ai/sdk`, без агентних фреймворків | LangChain та подібні ховають рівно те, що треба зрозуміти: цикл, збірку контексту, обробку tool calls |
| CLI розділений на `run` і `reply` | два процеси фізично не дають зробити `await prompt()` посеред циклу; це і є тест на коректність персистенції |
| Telegram відкладено до фази 6 | бот нічого не вчить про агентів, це просто транспорт I/O |
| `Channel` як порт з першого дня | коштує два типи й нуль часу, робить додавання Telegram справою на 50 рядків |
| `ask_human` — звичайний інструмент | один механізм покриває «підтверди план», «яку бібліотеку взяти» і «CI впав, що робимо» |
| `access: read \| write` у реєстрі інструментів | на фазі 3 захист стоятиме в коді, а не в надії, що модель прочитала промпт |
| Сховище — JSON-файли, не SQLite | інструмент має бути відповіддю на конкретну проблему; перехід почнеться з `agent list` або резидентного воркера |
| Журнал рішень — `.devflow/DECISIONS.md` у цільовому репо, не база агента | версіонується з кодом, рев'ються в PR, шариться через `git pull`; нуль синхронізації |
| Карта коду — кеш поза git (`~/.devflow/<repo>/map/`), не файл у репозиторії | похідні дані не комітять: щокоміта змінюються, дають конфлікти й шум у диффах. Спільний обʼєктний кеш за SHA — коли над репо працює команда |
| Тригер оновлення журналу — мерж PR, не коміт | рішення народжується на рівні PR; вдесятеро дешевше й чистіший сигнал |
| Агент не видаляє записи журналу сам | тільки позначає «суперечить коду» і віддає людині через `ask_human` |
| Борд (ClickUp/Trello) і чат (Telegram) — за портами | це транспорт, вибір відкладається; той самий прийом, що з `Channel` |
| Агент кодить сам, рушій за портом `Executor` | контракт «задача → гілка з комітами», тому свій цикл і Claude Agent SDK взаємозамінні; вибір за даними, поріг — третина задач не проходить з двох спроб |
| Внутрішній діалект LLM — Anthropic, інші вендори адаптуються до нього | «нейтральний» тип у цій області завжди або чийсь діалект, або каліка: губляться thinking, керування кешем, серверні інструменти. Обираємо одну мову, решту перекладаємо |
| Мультирепо: репо як параметр, стан за remote URL | один агент на репо; той самий проєкт у двох теках — одна памʼять |
| devflow-agent — полігон механіки, не полігон карти | 1000 рядків влазять у контекст 85 разів: карта тут не заощадить нічого. Але коміти, PR і ворота тестуємо на собі, додаючи кожну фічу |

## Архітектура

```
cli.ts (composition root: тут і тільки тут обираються реалізації)
   │
   ▼
agent/loop.ts   advance() / resume() / retry()  — єдине місце рішень
   │
   ├── Llm       agent/llm.ts       realLlm · scriptedLlm · demoLlm
   ├── Storage   db/storage.ts      FileStorage → SqliteStorage
   └── Channel   agent/channel.ts   CliChannel → TelegramChannel

agent/tools.ts  реєстр: опис для моделі + виконавець + access
agent/types.ts  runSchema (zod) → type Run
```

Правило залежностей: стрілки йдуть тільки вниз, до типів. `loop.ts` ніколи не
імпортує `FileStorage` чи `Anthropic` — тільки `Storage` і `Llm`.

### Мультирепо

Репозиторій — параметр, ніколи не глобальний стан і ніколи не `process.cwd()`
усередині коду.

```
~/.devflow/github.com--org--repo/     приватне, поза git
  runs/*.json      стан прогонів
  spans/*.jsonl    трейси
  config.json      chat id, board id, токени

цільове репо/.devflow/                комітиться
  DECISIONS.md     журнал рішень
  config.yml       гілки, ворота, дозволи
```

Одна тека в чужому репозиторії: легко ігнорувати або видалити цілком.

Ідентичність — нормалізований remote URL, не шлях: той самий проєкт у двох
теках має бути одним агентом. Без remote — хеш абсолютного шляху.

Ізоляція: окремі теки стану, `DECISIONS.md` тільки з репо в скоупі, перевірка
кореня у файлових інструментах.

Кілька процесів чи один із мультиплексуванням — рішення фази 4. Сьогодні
достатньо не хардкодити репо як глобальний стан. Підагенти лягають сюди
`parentRunId`-ом плюс дешевшою моделлю через наявний `Llm`.

### Інші вендори моделей

Порт `Llm` ізолює місце виклику, але його типи вендорські навмисно. `OpenAiLlm`
буде адаптером до внутрішнього діалекту Anthropic: `content`-блоки → `content` +
`tool_calls`, `tool_result` у `user` → повідомлення `role: "tool"`, `is_error` →
текстом, `stop_reason: "tool_use"` → `finish_reason: "tool_calls"`. Без
еквівалента — thinking-блоки і явне керування кешем. ~200–300 рядків в одному
файлі, ядро не змінюється. `AgentSdkExecutor` буде Anthropic-only за
визначенням.

### Board: квиток як одиниця роботи

Порт у `src/board/`. Першою реалізацією буде `GitHubBoard`, далі GitLab і решта.
GitHub обраний не через ціну: агенту в будь-якому разі потрібен доступ до
репозиторію для гілок і PR, тож квитки там означають одну автентифікацію замість
двох, нативний звʼязок `Closes #142` і розмову поруч із діффом.

У провайдерів по-різному влаштоване рівно те, що нам потрібно:

| | квиток | статус | розмова |
|---|---|---|---|
| GitHub | issue | поле в Projects v2 | коментарі issue |
| GitLab | issue | мітка або дошка | коментарі |
| Trello | картка | список | коментарі |

Тому `TicketStatus` (`todo`/`in_progress`/`in_review`/`blocked`/`done`) наш
власний, а відповідність колонкам провайдера задається в `.devflow/config.json`,
не в коді. JSON, а не YAML: у Node немає вбудованого парсера, а полів вісім.
`externalId` — рядок: у GitHub число, у Trello shortLink, у GitLab iid.

**Ліміти GitHub** (звіряти з документацією, вони змінюються): REST 5000/год на
токен, GraphQL 5000 балів/год, створення контенту ~80/хв і ~500/год, Search
30/хв, не більше 100 одночасних запитів. Відповідь 304 на умовний запит з ETag
у ліміт не рахується — тому полінг раз на 30 секунд коштує майже нічого.

**Реалізовано** у `src/board/github/`: `http.ts` — клієнт на голому `fetch` з
умовними запитами по ETag; `projects.ts` — GraphQL для Projects v2;
`board.ts` — `GitHubBoard`. Без `octokit`: потрібні лише issues, коментарі й
кілька GraphQL-запитів, зате потрібен явний контроль ETag.

**Пастка Projects v2:** дошка доступна тільки через GraphQL, issues — через
REST. Статус там кастомне поле single-select, тому `projectId`, `fieldId` і
`optionId` кожної колонки розвʼязуються один раз на процес і кешуються. Issue,
створений агентом, не потрапляє на дошку сам — його треба додати
`addProjectV2ItemById`.

**Колонки шаблону Kanban** лягли вдало: `Backlog` агент не бачить взагалі, тож
перетягування картки в `Ready` — це і є жест «починай». Запуск роботи мишею,
а не командою.

**Логін власника токена** визначається через `/user` і кешується: без нього
агент прийме власне питання за відповідь людини.

**Ідемпотентність** — маркер `<!-- devflow run:<id> step:<step> -->` у тілі
коментаря чи issue плюс запис зовнішнього id у себе **до** того, як результат
піде в модель. Потрібен разом із першою write-дією, не «на фазі 3»: планувальник
повертає обірвані runs у чергу, і без маркера повтор створить дубль.

### Планувальник

`devflow watch` — один процес на машині, `src/scheduler.ts`. Оберт складається з
трьох дій: забрати нові квитки зі списку готових, підібрати відповіді людини з
коментарів, і, якщо ніщо не крутиться, взяти найстаріший `queued`.

**Одна активна робота, але скільки завгодно припаркованих.** Агент зайнятий,
лише поки крутиться `advance`. Щойно run стає `waiting_human`, планувальник
вільний і бере наступний квиток — очікування відповіді нічого не блокує.

**Відновлення після простою.** На старті run у статусі `running` означає, що
процес помер посеред роботи, і повертається в `queued`. Безпечно, поки агент
упав до зовнішньої дії; після створення issue чи пуша повтор зробить дубль —
тому маркер ідемпотентності потрібен разом із першою write-дією.

**Дублі квитків** відсікаються за `ticket ref`: якщо на цей квиток уже є
незавершений run, новий не створюється.

**Канал у цьому режимі — коментарі під квитком** (`BoardChannel`). Питання й
фінальний звіт стають коментарями, проміжні кроки — ні, інакше квиток
перетворюється на лог. Відповідь людини — перший чужий коментар після
`pending.askedAt`; свої позначені `mine`, щоб полінг не відповідав сам собі.

### Захист від змішування репозиторіїв

Один проєкт може жити на GitHub і GitLab одночасно, а в репо може бути кілька
remote. Чотири запобіжники, усі fail closed:

```
remote названий явно      config.git.remote (типово origin) — репо з кількома
                          remote мусить сказати, який його

звірка на старті          конфіг каже github:org/repo, а remote веде на
                          gitlab.com → відмова з поясненням, не здогад
                          ← найнебезпечніший випадок: читає одну дошку, пише
                            в інший хост

run знає своє репо        Run.repo { id, remote }; перед resume і retry
                          звіряється з поточним. Поки стан лежить у теці на
                          кожне репо, розділення тримається на структурі
                          файлів — після спільної бази ця гарантія зникне,
                          тому привʼязка зроблена раніше за базу

нормалізація URL          https://, git@, ssh://git@ зводяться до host/path
                          порядок очищення важливий: спершу протокол, потім
                          user@, інакше хостом стає "git@github.com"
```

Старі runs без привʼязки проходять: вони лежать у теці свого репо, і це
достатня гарантія до переходу на базу.

### Executor: межа проходить по git

Порт визначається результатом у git, а не кроками — інакше реалізації не
взаємозамінні:

```ts
type Task = { title: string; description: string; files?: string[] };
type Outcome = {
  branch: string;
  changedFiles: string[];
  summary: string;
  cost: { inputTokens: number; outputTokens: number };
};

interface Executor {
  execute(task: Task, ctx: RepoContext): Promise<Outcome>;
}
```

`OwnExecutor` — власний цикл із `write_file` / `edit_file` / `run_command`.
`AgentSdkExecutor` — делегування. Назовні обидва віддають гілку з комітами; далі
однаково: ворота, рев'ю дифа, PR.

Перемикач: глобально (`AGENT_EXECUTOR`), на репо (`.devflow/config.yml`), на
задачу (за розміром плану), ескалацією. Ескалація основна — дешевший пробує
першим, після двох провалів воріт задача йде на дорожчий: не треба вгадувати
наперед і зʼявляється статистика, скільки закриває власний цикл.

Повтор починається з чистої гілки — `git reset` частина контракту, а не деталь
реалізації. Відкат це git, а не рушій.

## Трасування

Реалізовано: `src/trace/` — `Span`, порт `TraceSink`, `FileSink` (JSONL на
прогін), `Tracer`, рендер у текст і HTML; команда `agent trace <id>`.

У `llm_call` лягає весь `response.content`, а не лише `stop_reason`: саме там
видно, що модель вирішила й написала. У терміналі показується однорядковий
підсумок (текст відповіді або «просить: read_file»), у HTML рядок розгортається
кліком на повний вміст. Вивід інструмента обрізається на 4000 символах.

Спани обслуговують і облік вартості, і дерево виконання, тому формат такий:

```ts
type Span = {
  id: string;
  runId: string;
  parentId: string | null;   // ← дає дерево
  type: "llm_call" | "tool_call" | "question" | "answer" | "gate" | "executor";
  name: string;              // "read_file", "npm test", "claude-opus-5"
  startedAt: number;
  endedAt: number | null;
  input: unknown;
  output: unknown;
  error: string | null;
  cost: { inputTokens: number; outputTokens: number } | null;
};
```

`parentId` потрібен одразу, не «колись»: дерево дають паралельні виклики в одній
відповіді, ескалація `Executor` і підагенти.

**Вигляд — водоспад із вкладеністю, не граф вузлів:** важать час і гроші. Голий
HTML і CSS grid; React Flow — тільки якщо знадобиться вільне полотно з ребрами.
Для налагодження дешевше слати спани в Langfuse — готовий viewer без роботи
над UI.

«Рішення» — це обраний інструмент, його аргументи й текст. Самі міркування дає
`thinking: { type: "adaptive", display: "summarized" }`, за перемикачем: коштує
токени.

Сховище — порт `TraceSink`, один `JSONL` на прогін: `FileSink` зараз,
`S3Sink` / `GcsSink` / `LangfuseSink` потім. База потрібна лише для списку й
фільтрів. Amazon чи Google ні на що не впливає — обидва це `PutObject` плюс
підписаний URL.

У спанах лежать промпти, вміст файлів і діфи. Поле «що можна показувати» й
термін зберігання закладаються в схему одразу, інакше при першому виїзді за межі
машини переписувати все накопичене.

## Системний промпт

Варіанти в `src/agent/prompt.ts`, типово `v4` (`v3` плюс правило про
`<untrusted>`). Міняти тільки за виміряним
прогоном: `npm run ab -- v1 v3` ганяє однакові питання на кожному варіанті й
рахує посилання на файли, читання і вартість.

**Міряти якість, а не проксі.** Перша спроба порівнювала кількість читань
файлів — і показала, що `v2` читає більше й коштує на 45% дорожче, хоча
конкретна проблема не зникла. Метрика «чи є у відповіді шлях до файлу» одразу
розвела варіанти: 1/3 → 2/3 → 3/3.

Що спрацювало у `v3` і не спрацювало раніше: **жорстка перша дія** («перша дія в
кожній задачі — list_files, без винятків») замість заборони («опис інструмента
підставою не є»). Позитивна інструкція про порядок дій виявилась сильнішою за
заборону — і дешевшою, бо модель одразу бачить структуру замість того, щоб
намацувати шляхи.

Результати заміру на `claude-haiku-4-5`, три питання:

| | посилання | читань | без читання | $ |
|---|---|---|---|---|
| v1 | 1/3 | 5 | 1 | 0.0467 |
| v2 | 2/3 | 8 | 1 | 0.0635 |
| v3 | 3/3 | 7 | 0 | 0.0611 |

Три питання без повторів — числа орієнтовні, не статистика. Для близьких
варіантів потрібні повтори.

## Конвенції коду

- ESM (`"type": "module"`), імпорти без розширень, запуск через `tsx`.
- `strict` + `noUncheckedIndexedAccess`. `content[0]` завжди `T | undefined`.
- Типи SDK використовуємо як є: `Anthropic.MessageParam`, `Anthropic.Message`,
  `Anthropic.ToolResultBlockParam`. Свої аналоги не оголошуємо.
- zod на межах довіри: диск, GitHub, відповіді моделі. Усередині — звичайні типи.
- Тип виводиться зі схеми через `z.infer`, а не пишеться руками паралельно.
- Помилки — класи (`RunNotFound`, `VersionConflict`, `NotWaiting`), не рядки.
- Нове поле в `runSchema` додається з `.default(...)`, щоб старі файли читались.

## Правило памʼяті

Стосується і `DECISIONS.md` у цільовому репо, і `CLAUDE.md` з `ROADMAP.md` тут.

### Де що лежить

```
~/.devflow/<repo-slug>/     приватне, поза git
  runs/*.json               стан прогонів
  spans/*.jsonl             трейси
  config.json               chat id, board id, токени

репозиторій/                комітиться
  CLAUDE.md                 правила й напрям   ← пише людина/агент у розмові
  .devflow/DECISIONS.md     локальні знахідки  ← пише агент на мерж PR
```

**Межа між `CLAUDE.md` і `DECISIONS.md` — наявність якоря.** Запис, який можна
прибити до конкретного місця в коді (`Де: src/auth/verify.ts → verifyToken`),
іде в `DECISIONS.md`. Запис про систему загалом, якому нема куди поставити
якір, — у `CLAUDE.md`.

Приклад: «внутрішній діалект LLM — Anthropic» стосується всієї системи, якоря
не має → `CLAUDE.md`. «Токени валідуються тільки у `verify.ts`, бо розʼїхались
дві копії» прибите до файлу → `DECISIONS.md`.

Різні й життєві цикли: `CLAUDE.md` змінюється рідко й читається цілком щосесії;
`DECISIONS.md` дописується після кожного мержу, росте постійно, читається
вибірково.

### Карта коду — кеш, не репозиторій

Карта виводиться з коду, журнал — ні. Тому вони лежать по-різному:

```
DECISIONS.md   написаний        → цільове репо/.devflow/, комітиться
карта коду     вирахувана       → ~/.devflow/<repo>/map/, не комітиться
```

Похідні дані в git не кладуть — з тієї ж причини, що `node_modules` і `dist`:
карта змінюється щокоміта, дає конфлікти злиття й засмічує кожен diff шумом,
який ніхто не рев'ює.

Три поверхи зберігання, у порядку появи потреби:

1. `~/.devflow/<repo-slug>/map/` — нуль інфраструктури; мінус у тому, що кожна
   людина будує свою копію й платить за це;
2. у репо під git — не робимо, див. вище;
3. спільний обʼєктний кеш `s3://…/<repo>/<commit-sha>/map.jsonl` — будується раз,
   тягнеться всією командою, ключ за SHA, тож протухання само собою. Вмикати,
   коли над репо працює більше однієї людини.

Формат — запис на файл, не суцільний текст:

```
~/.devflow/<repo>/map/
  index.jsonl   { path, sha, exports[], imports[], summary }
  meta.json     built_at, head_sha
```

Погранульно саме заради інкрементального оновлення: новий коміт → `git diff` дає
список змінених файлів → переаналізовуються тільки вони. Суцільний текст
довелося б перегенеровувати цілком.

Карта має сенс лише коли проєкт не влазить у контекст. Поки влазить — агент
читає файли напряму, і це дешевше за побудову й підтримку карти.

### Що записувати

**Записуємо, якщо рішення нетривіальне й не зрозуміле з коду.** Практичний
поріг: новій людині знадобилось би понад пʼятнадцять хвилин дійти до цього
самому, і `grep` на це не відповідає.

Не записуємо: структуру коду, назви файлів, те, що видно з типів, історію
рефакторингів, які нічого не змінили в підході.

У промптах агента «нічого не записувати» має бути окремим валідним варіантом
відповіді: модель, яку спитали «що тут варто зафіксувати», завжди щось напише.

**Актуалізація — частина роботи.** Після кожного помітного кроку пройтись по
`CLAUDE.md`, `ROADMAP.md`, `CHECKLIST.md`, `README.md` і виправити розбіжності з
кодом: списки файлів і команд, номери рядків, лічильники перевірок, статуси фаз,
а також суперечності між твердженнями всередині файлу. Застаріла документація
гірша за відсутню — за нею діють як за правдою.

Формат запису:

```markdown
## Токени валідуються в одному місці
**Де:** src/auth/verify.ts → verifyToken
**Чому:** було дві копії перевірки, розʼїхались після зміни TTL —
прод три дні пускав протерміновані токени.
**Не роби:** не додавай перевірку в middleware.
**PR:** #142
```

`Де` — якір. Механізму інвалідації немає навмисно: агент, беручи запис у роботу,
все одно відкриває цей файл і бачить зникнення символа тоді, коли це важить.
Журнал — підказка, ніколи не джерело правди.

## Правила надійності

- Помилка інструмента → `tool_result` з `is_error: true`, не кидається вгору:
  найдешевша самокорекція.
- Помилка виклику моделі → `status: "failed"` плюс причина в `run.error`. Run
  ніколи не лишається в `running` назавжди.
- `maxSteps` обовʼязковий: інакше крива модель спалює бюджет мовчки.
- `save()` після кожного кроку, не в кінці.
- Untrusted input: чужий текст іде в контекст загорнутим у
  `<untrusted source="...">…</untrusted>`; закриваючий тег усередині вмісту
  знешкоджується, інакше його можна підробити. Реалізовано для `read_file`
  (`untrusted()` у `agent/tools.ts`); для тіл issues і коментарів — при
  підключенні GitHub. Правило для моделі — у промпті `v4`.
- Ідемпотентність: маркер у тілі issue (`<!-- run:run_123 task:4 -->`) плюс запис
  зовнішнього id у власну таблицю до того, як результат віддається моделі.

## Команди

Один раз: `npm link` у теці проєкту — і `devflow` доступний звідусіль.
Репозиторій визначається поточною текою, як у `git`.

```bash
cd ~/projects/будь-що
devflow auth                # записати токени в ~/.devflow/.env
devflow run "<задача>"      # створити run і працювати до паузи
devflow reply <id> "<текст>"
devflow retry <id>
devflow board               # звʼязок із дошкою: готові квитки
devflow watch               # планувальник: дошка → черга → робота
devflow list                # усі runs цього репозиторію
devflow trace <id>          # дерево кроків, час і вартість
devflow show <id>

npm run typecheck           # у теці devflow-agent

npm run try-wire      # справжній HTTP-запит через локальний сервер-підміну
npm run try-storage   # 14 перевірок FileStorage
npm run try-tools     # 14 перевірок реєстру інструментів
npm run try-llm       # 7 перевірок підробленої моделі
npm run try-board     # 11 перевірок порту дошки
npm run try-watch     # 12 перевірок планувальника
npm run try-github    # 9 перевірок мапінгу GitHub (без мережі)
npm run try-guard     # 11 перевірок захисту від змішування репо
npm run try-loop      # 25 перевірок циклу
```

Змінні: `AGENT_LLM=demo` (офлайн-модель, без витрат), `MODEL`, `MAX_STEPS`.
Стан runs — у `.runs/`, трейси — у `.runs/traces/<runId>.jsonl`, поза git.

Діагностика запиту: `ANTHROPIC_LOG=debug npm run ping` — вбудоване логування SDK,
але глибше двох рівнів вкладеності воно згортає; тоді `try-wire`.
