# devflow-agent

AI Software Development Manager — агентна система, що веде життєвий цикл розробки
для одного розробника або малої команди.

**Навчальна мета важливіша за продукт.** Домен зафіксовано один і він тягнеться
крізь усі фази, щоб кожна нова тема лягала на той самий проєкт.

Поточна позиція, фази й відкриті питання — у `ROADMAP.md`.
Перевірки й потоки даних — у `CHECKLIST.md`.

## Як працювати з користувачем

TypeScript-розробник. Спілкування українською. Весь код — TS зі строгими типами.

Формат відповіді:

1. спочатку візуальна схема (діаграма, флоучарт, архітектура), якщо тема це дозволяє;
2. під схемою коротке пояснення на 2–4 речення, без води;
3. далі практичний приклад коду.

Мінімум заголовків і bullet-списків. Складну концепцію розбивати на кроки, кожен
зі своєю схемою.

**Мета — навчитись, а не отримати готовий код.** Не давай команд і конфігів без
пояснення, що саме вони роблять. Питання «що це за файли» — не претензія, а
сигнал сповільнити темп. Краще менше коду з розбором, ніж великий блок для
копіювання.

**Перепитуй перед тим, як щось робити.** Користувач попросив явно. Перед новим
файлом, рефакторингом чи зовнішньою дією — коротко опиши план і дочекайся «так».

**Коміти** пишемо без трейлерів `Co-Authored-By` і `Claude-Session`. Автор —
`skipokylas <skipokylas@gmail.com>`, задано локально в цьому репозиторії.
Push тільки після явного дозволу.

## Що будуємо

Сценарій MVP, який має запрацювати end-to-end:

1. користувач підключає GitHub-репозиторій;
2. надсилає запит на фічу (канонічний приклад: «додати passwordless-авторизацію
   через email magic links»);
3. агент читає репозиторій і документацію;
4. генерує acceptance criteria та план;
5. користувач переглядає й підтверджує план;
6. агент створює GitHub issues без дублікатів;
7. розробник відкриває PR, повʼязаний з issue;
8. агент відстежує статуси рев'ю та CI;
9. повідомляє про впалі перевірки й блокери;
10. після мержу готує release notes;
11. усі дії доступні в аудит-лозі.

## Закриті рішення

Не переглядати без явного запиту користувача.

| Рішення | Чому |
|---|---|
| TypeScript, не Python | основна мова користувача; мета — зрозуміти архітектуру, а не боротись із мовою |
| Голий `@anthropic-ai/sdk`, без агентних фреймворків | LangChain та подібні ховають рівно те, що треба зрозуміти: цикл, збірку контексту, обробку tool calls |
| CLI розділений на `run` і `reply` | два процеси фізично не дають зробити `await prompt()` посеред циклу; це і є тест на коректність персистенції |
| Telegram відкладено до фази 6 | бот нічого не вчить про агентів, це просто транспорт I/O |
| `Channel` як порт з першого дня | коштує два типи й нуль часу, робить додавання Telegram справою на 50 рядків |
| `ask_human` — звичайний інструмент | один механізм покриває «підтверди план», «яку бібліотеку взяти» і «CI впав, що робимо» |
| `access: read \| write` у реєстрі інструментів | на фазі 3 захист стоятиме в коді, а не в надії, що модель прочитала промпт |
| Сховище — JSON-файли, не SQLite | інструмент має бути відповіддю на конкретну проблему; перехід почнеться з `agent list` |

## Архітектура

```
cli.ts (composition root: тут і тільки тут обираються реалізації)
   │
   ▼
agent/loop.ts   advance() / resume() / retry()  — єдине місце рішень
   │
   ├── Llm       agent/llm.ts       realLlm · scriptedLlm · demoLlm
   ├── Storage   db/storage.ts      FileStorage → SqliteStorage
   └── Channel   agent/channel.ts   CliChannel → TelegramChannel

agent/tools.ts  реєстр: опис для моделі + виконавець + access
agent/types.ts  runSchema (zod) → type Run
```

Правило залежностей: стрілки йдуть тільки вниз, до типів. `loop.ts` ніколи не
імпортує `FileStorage` чи `Anthropic` — тільки `Storage` і `Llm`.

## Конвенції коду

- ESM (`"type": "module"`), імпорти без розширень, запуск через `tsx`.
- `strict` + `noUncheckedIndexedAccess`. `content[0]` завжди `T | undefined`.
- Типи SDK використовуємо як є: `Anthropic.MessageParam`, `Anthropic.Message`,
  `Anthropic.ToolResultBlockParam`. Свої аналоги не оголошуємо.
- zod на межах довіри: диск, GitHub, відповіді моделі. Усередині — звичайні типи.
- Тип виводиться зі схеми через `z.infer`, а не пишеться руками паралельно.
- Помилки — класи (`RunNotFound`, `VersionConflict`, `NotWaiting`), не рядки.
- Нове поле в `runSchema` додається з `.default(...)`, щоб старі файли читались.

## Правила надійності

- Помилка інструмента вертається в модель як `tool_result` з `is_error: true`,
  а не кидається вгору. Це найдешевша самокорекція.
- Помилка виклику моделі → `status: "failed"` плюс причина в `run.error`.
  Run ніколи не лишається в `running` назавжди.
- `maxSteps` обовʼязковий: крива модель інакше спалює бюджет мовчки.
- `save()` після кожного кроку, не в кінці.
- Untrusted input: усе з GitHub (README, тіла issues, коментарі) потрапляє в
  контекст загорнутим у `<untrusted source="...">…</untrusted>`.
- Ідемпотентність: маркер у тілі issue (`<!-- run:run_123 task:4 -->`) плюс запис
  зовнішнього id у власну таблицю до того, як результат віддається моделі.

## Команди

```bash
npm run typecheck                     # tsc --noEmit
npm run dev -- run "<задача>"         # створити run і працювати до паузи
npm run dev -- reply <id> "<текст>"   # продовжити run, що чекає на людину
npm run dev -- retry <id>             # повторити перерваний run
npm run dev -- show <id>              # стан run

npm run try-wire      # справжній HTTP-запит через локальний сервер-підміну
npm run try-storage   # 11 перевірок FileStorage
npm run try-tools     # 9 перевірок реєстру інструментів
npm run try-llm       # 7 перевірок підробленої моделі
npm run try-loop      # 13 перевірок циклу
```

Змінні оточення: `AGENT_LLM=demo` (офлайн-модель, без витрат), `MODEL`,
`MAX_STEPS`. Стан runs — у `.runs/`, поза git.

Для швидкої діагностики запиту: `ANTHROPIC_LOG=debug npm run ping` — вбудоване
логування SDK; глибше двох рівнів вкладеності воно згортає, тоді `try-wire`.
