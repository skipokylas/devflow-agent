# devflow-agent

AI Software Development Manager — агентна система, що веде життєвий цикл розробки
для одного розробника або малої команди.

**Дві мети однакової ваги: працюючий продукт і розуміння того, як він
влаштований.** Не жертвувати жодною. Не давати готовий код без пояснення — але й
не зупинятись на навчальних прикладах там, де потрібна робоча фіча.

Домен зафіксовано один і він тягнеться крізь усі фази, щоб кожна нова тема
лягала на той самий проєкт.

Поточна позиція, фази й відкриті питання — у `ROADMAP.md`.
Перевірки й потоки даних — у `CHECKLIST.md`.

## Як працювати з користувачем

TypeScript-розробник. Спілкування українською. Весь код — TS зі строгими типами.

Формат відповіді:

1. спочатку візуальна схема (діаграма, флоучарт, архітектура), якщо тема це дозволяє;
2. під схемою коротке пояснення на 2–4 речення, без води;
3. далі практичний приклад коду.

Мінімум заголовків і bullet-списків. Складну концепцію розбивати на кроки, кожен
зі своєю схемою.

**Пояснення обовʼязкове, зупинка на прикладах — ні.** Код і конфіги йдуть із
розбором, що саме вони роблять; питання «що це за файли» — не претензія, а
сигнал сповільнити темп і розібрати детальніше. Але там, де потрібна робоча
фіча, доводимо її до робочого стану, а не лишаємо навчальний приклад.

Практично: не великий блок для копіювання, а робочий код, поданий частинами
з поясненням кожної.

**Перепитуй перед тим, як щось робити.** Користувач попросив явно. Перед новим
файлом, рефакторингом чи зовнішньою дією — коротко опиши план і дочекайся «так».

**Коміти** пишемо без трейлерів `Co-Authored-By` і `Claude-Session`. Автор —
`skipokylas <skipokylas@gmail.com>`, задано локально в цьому репозиторії.
Push тільки після явного дозволу.

## Продукт

Один агент на один репозиторій. Пʼять здатностей, у порядку залежності:

1. **Журнал рішень.** Агент веде `DECISIONS.md` у цільовому репозиторії — те, чого
   не видно з коду: чому зроблено саме так, які інваріанти не можна ламати, що
   вже пробували й відкинули. Файл лежить поруч із кодом, версіонується з ним,
   приходить тим самим PR. Нова людина в проєкті отримує його безкоштовно
   через `git pull`.
2. **Ведення задач.** Опис → підзадачі → картки на борді → виконання. Коли
   бракує вхідних даних, агент пише в чат і продовжує автономно одразу після
   відповіді.
3. **Верифікація.** Ворота якості за зростанням ціни: typecheck і тести → білд →
   браузер. Браузер останній: він відповідає на те, чого не покриють тести, але
   повільний і крихкий.
4. **Прозорість.** Кожен прогін лишає дерево кроків: які інструменти викликано,
   з якими аргументами, що повернули, скільки коштували, де агент питав людину.
   Посилання виду `/trace/<runId>` привʼязане до задачі.
5. **Коміти й PR.** Гілка на задачу, ніколи не в `main`, PR як одиниця рев'ю.

**Агент кодить сам** — переводить текстовий опис у зміни в коді. Рушій
редагування захований за портом `Executor` (див. нижче): v1 — власний цикл,
делегування Claude Agent SDK лишається другою реалізацією й вмикається за
даними, а не наперед.

## Сценарій MVP

Має запрацювати end-to-end:

1. користувач підключає GitHub-репозиторій;
2. надсилає запит на фічу (канонічний приклад: «додати passwordless-авторизацію
   через email magic links»);
3. агент читає репозиторій і документацію;
4. генерує acceptance criteria та план;
5. користувач переглядає й підтверджує план;
6. агент створює GitHub issues без дублікатів;
7. розробник відкриває PR, повʼязаний з issue;
8. агент відстежує статуси рев'ю та CI;
9. повідомляє про впалі перевірки й блокери;
10. після мержу готує release notes;
11. усі дії доступні в аудит-лозі.

## Закриті рішення

Не переглядати без явного запиту користувача.

| Рішення | Чому |
|---|---|
| TypeScript, не Python | основна мова користувача; мета — зрозуміти архітектуру, а не боротись із мовою |
| Голий `@anthropic-ai/sdk`, без агентних фреймворків | LangChain та подібні ховають рівно те, що треба зрозуміти: цикл, збірку контексту, обробку tool calls |
| CLI розділений на `run` і `reply` | два процеси фізично не дають зробити `await prompt()` посеред циклу; це і є тест на коректність персистенції |
| Telegram відкладено до фази 6 | бот нічого не вчить про агентів, це просто транспорт I/O |
| `Channel` як порт з першого дня | коштує два типи й нуль часу, робить додавання Telegram справою на 50 рядків |
| `ask_human` — звичайний інструмент | один механізм покриває «підтверди план», «яку бібліотеку взяти» і «CI впав, що робимо» |
| `access: read \| write` у реєстрі інструментів | на фазі 3 захист стоятиме в коді, а не в надії, що модель прочитала промпт |
| Сховище — JSON-файли, не SQLite | інструмент має бути відповіддю на конкретну проблему; перехід почнеться з `agent list` або резидентного воркера |
| Журнал рішень — `.devflow/DECISIONS.md` у цільовому репо, не база агента | версіонується з кодом, рев'ються в PR, шариться через `git pull`; нуль синхронізації |
| Тригер оновлення журналу — мерж PR, не коміт | рішення народжується на рівні PR; вдесятеро дешевше й чистіший сигнал |
| Агент не видаляє записи журналу сам | тільки позначає «суперечить коду» і віддає людині через `ask_human` |
| Борд (ClickUp/Trello) і чат (Telegram) — за портами | це транспорт, вибір відкладається; той самий прийом, що з `Channel` |
| Агент кодить сам, рушій за портом `Executor` | контракт «задача → гілка з комітами», тому свій цикл і Claude Agent SDK взаємозамінні; вибір за даними, поріг — третина задач не проходить з двох спроб |
| Внутрішній діалект LLM — Anthropic, інші вендори адаптуються до нього | «нейтральний» тип у цій області завжди або чийсь діалект, або каліка: губляться thinking, керування кешем, серверні інструменти. Обираємо одну мову, решту перекладаємо |
| Мультирепо: репо як параметр, стан за remote URL | один агент на репо; той самий проєкт у двох теках — одна памʼять |
| devflow-agent — полігон механіки, не полігон карти | 1000 рядків влазять у контекст 85 разів: карта тут не заощадить нічого. Але коміти, PR і ворота тестуємо на собі, додаючи кожну фічу |

## Архітектура

```
cli.ts (composition root: тут і тільки тут обираються реалізації)
   │
   ▼
agent/loop.ts   advance() / resume() / retry()  — єдине місце рішень
   │
   ├── Llm       agent/llm.ts       realLlm · scriptedLlm · demoLlm
   ├── Storage   db/storage.ts      FileStorage → SqliteStorage
   └── Channel   agent/channel.ts   CliChannel → TelegramChannel

agent/tools.ts  реєстр: опис для моделі + виконавець + access
agent/types.ts  runSchema (zod) → type Run
```

Правило залежностей: стрілки йдуть тільки вниз, до типів. `loop.ts` ніколи не
імпортує `FileStorage` чи `Anthropic` — тільки `Storage` і `Llm`.

### Мультирепо

Один агент на один репозиторій: свій стан, свій чат, свій контекст. Репозиторій —
параметр, ніколи не глобальний стан і ніколи не `process.cwd()` усередині коду.

```
~/.devflow/                              приватне, поза git
  github.com--org--repo/
    runs/*.json      стан прогонів
    events.db        облік вартості
    config.json      chat id, board id, токени

цільове репо/                            комітиться, рев'ється в PR
  .devflow/
    DECISIONS.md     журнал рішень
    config.yml       гілкова політика, ворота, дозволені інструменти
```

Агент лишає в чужому репозиторії рівно одну теку: її легко додати в
`.gitignore`, якщо власники не хочуть її бачити, і легко видалити цілком.

Ідентичність репо — нормалізований remote URL, не шлях на диску: той самий
проєкт у двох теках має бути одним агентом з однією памʼяттю. Без remote —
хеш абсолютного шляху.

Ізоляція тримається на трьох барʼєрах: окремі теки стану, `DECISIONS.md`
читається лише з репо в скоупі, перевірка кореня в файлових інструментах.

Кілька процесів чи один із мультиплексуванням — рішення фази 4, разом із
воркером. Сьогоднішня дія одна: не хардкодити репо як глобальний стан.

Підагенти лягають сюди природно: спільний скоуп репо, власний стан прогону.
Тоді в `Run` додасться `parentRunId`, а дешевша модель для воркера — це вже
наявний порт `Llm`.

### Executor: межа проходить по git

Щоб дві реалізації були взаємозамінні, порт визначається не кроками, а
результатом у git:

```ts
type Task = { title: string; description: string; files?: string[] };
type Outcome = {
  branch: string;
  changedFiles: string[];
  summary: string;
  cost: { inputTokens: number; outputTokens: number };
};

interface Executor {
  execute(task: Task, ctx: RepoContext): Promise<Outcome>;
}
```

`OwnExecutor` — власний цикл із `write_file` / `edit_file` / `run_command`.
`AgentSdkExecutor` — делегування Claude Agent SDK. Назовні обидва віддають
гілку з комітами; далі однаково: ворота, рев'ю дифа, PR.

Перемикач на чотирьох рівнях: глобально (`AGENT_EXECUTOR`), на репо
(`.devflow.yml`), на задачу (за розміром плану), і **ескалацією** — дешевший
виконавець пробує першим, після двох провалів воріт та сама задача йде на
дорожчий. Ескалація основна: вона не вимагає вгадувати наперед і сама дає
статистику, скільки задач власний цикл закриває сам.

Умова, без якої ескалація не працює: **повтор починається з чистої гілки**.
`git reset` перед другою спробою — частина контракту, а не деталь реалізації.

Відкат — це git, а не рушій. Гілка на задачу плюс `reset` дають повний відкат
за будь-якого виконавця.

## Трасування: одна таблиця, два споживачі

`events` обслуговує і облік вартості, і дерево виконання. Тому формат — спани,
а не плоский лог:

```ts
type Span = {
  id: string;
  runId: string;
  parentId: string | null;   // ← дає дерево
  type: "llm_call" | "tool_call" | "question" | "answer" | "gate" | "executor";
  name: string;              // "read_file", "npm test", "claude-opus-5"
  startedAt: number;
  endedAt: number | null;
  input: unknown;
  output: unknown;
  error: string | null;
  cost: { inputTokens: number; outputTokens: number } | null;
};
```

`parentId` потрібен не «колись»: дерево зʼявляється одразу в трьох місцях —
паралельні виклики інструментів в одній відповіді, ескалація на другий
`Executor`, підагенти.

**Вигляд — водоспад із вкладеністю, не граф вузлів.** Осі, які важать, — час і
гроші; усі trace-viewer'и зійшлись на цьому не випадково. Робиться на голому
HTML і CSS grid. React Flow (xyflow) знадобиться, тільки якщо колись буде
потрібне вільне полотно з ребрами — до того це складність без користі.

Для налагодження дешевий проміжний крок — слати спани в Langfuse
(open source, self-hosted): повноцінний trace-viewer без роботи над UI.

**Що показувати як «рішення».** Думки моделі за замовчуванням не повертаються.
Доступні: обраний інструмент, його аргументи, згенерований текст. Для самих
міркувань є `thinking: { type: "adaptive", display: "summarized" }` — вмикати
перемикачем, бо це коштує токени.

**Інші вендори моделей.** Порт `Llm` ізолює місце виклику (одне на проєкт), але
його типи — вендорські навмисно. `OpenAiLlm` буде адаптером до внутрішнього
діалекту Anthropic: `content`-блоки → `content` + `tool_calls`, `tool_result` у
`user` → окреме повідомлення `role: "tool"`, `is_error` → текстом (прапорця
немає), `stop_reason: "tool_use"` → `finish_reason: "tool_calls"`. Без
еквівалента лишаються thinking-блоки і явне керування кешем. Приблизно 200–300
рядків в одному файлі; `loop.ts`, `tools.ts` і `storage.ts` не змінюються.
Окремо: `AgentSdkExecutor`, якщо колись зʼявиться, буде Anthropic-only за
визначенням — мультивендорність можлива на рівні `Llm`, не на рівні готового
кодинг-рушія.

**Сховище — порт `TraceSink`.** Спани незмінні й append-only, тому один `JSONL`
на прогін: `FileSink` зараз, `S3Sink` / `GcsSink` / `LangfuseSink` потім. Вибір
між Amazon і Google ні на що не впливає — обидва це `PutObject` і підписаний
URL; вирішувати з появою першого платного користувача. База потрібна лише для
списку й фільтрів, не для перегляду.

**Застереження.** У спанах лежать промпти, вміст файлів і діфи — чужий код.
Поле «що можна показувати» й термін зберігання закладаються в схему одразу:
інакше при першому ж виїзді за межі машини доведеться переписувати всі
накопичені трейси.

## Конвенції коду

- ESM (`"type": "module"`), імпорти без розширень, запуск через `tsx`.
- `strict` + `noUncheckedIndexedAccess`. `content[0]` завжди `T | undefined`.
- Типи SDK використовуємо як є: `Anthropic.MessageParam`, `Anthropic.Message`,
  `Anthropic.ToolResultBlockParam`. Свої аналоги не оголошуємо.
- zod на межах довіри: диск, GitHub, відповіді моделі. Усередині — звичайні типи.
- Тип виводиться зі схеми через `z.infer`, а не пишеться руками паралельно.
- Помилки — класи (`RunNotFound`, `VersionConflict`, `NotWaiting`), не рядки.
- Нове поле в `runSchema` додається з `.default(...)`, щоб старі файли читались.

## Правило памʼяті

Стосується і `DECISIONS.md` у цільовому репозиторії, і `CLAUDE.md` з
`ROADMAP.md` тут.

### Де що лежить

```
~/.devflow/<repo-slug>/     приватне, поза git
  runs/*.json               стан прогонів
  spans/*.jsonl             трейси
  config.json               chat id, board id, токени

репозиторій/                комітиться
  CLAUDE.md                 правила й напрям   ← пише людина/агент у розмові
  .devflow/DECISIONS.md     локальні знахідки  ← пише агент на мерж PR
```

**Межа між `CLAUDE.md` і `DECISIONS.md` — наявність якоря.** Запис, який можна
прибити до конкретного місця в коді (`Де: src/auth/verify.ts → verifyToken`),
іде в `DECISIONS.md`. Запис про систему загалом, якому нема куди поставити
якір, — у `CLAUDE.md`.

Приклад: «внутрішній діалект LLM — Anthropic» стосується всієї системи, якоря
не має → `CLAUDE.md`. «Токени валідуються тільки у `verify.ts`, бо розʼїхались
дві копії» прибите до файлу → `DECISIONS.md`.

Різні й життєві цикли: `CLAUDE.md` змінюється рідко й читається цілком щосесії;
`DECISIONS.md` дописується після кожного мержу, росте постійно, читається
вибірково.

### Що записувати

**Записуємо, якщо рішення нетривіальне й не зрозуміле з коду.** Практичний
поріг: новій людині знадобилось би понад пʼятнадцять хвилин дійти до цього
самому, і `grep` на це не відповідає.

Не записуємо: структуру коду, назви файлів, те, що видно з типів, історію
рефакторингів, які нічого не змінили в підході.

Наслідки для промптів агента: «нічого не записувати» має бути окремим валідним
варіантом відповіді. Модель, яку спитали «що тут варто зафіксувати», завжди
щось напише — це найшвидший спосіб перетворити журнал на смітник.

**Актуалізація — частина роботи, не окреме завдання.** Після кожного помітного
кроку (нова фіча, змінене рішення, закрита фаза) пройтись по `CLAUDE.md`,
`ROADMAP.md`, `CHECKLIST.md` і `README.md` та виправити те, що розійшлось із
кодом. Перевіряти конкретно: списки файлів і команд, номери рядків у посиланнях,
кількість перевірок, «що є / чого немає», статуси фаз. Застаріла документація
гірша за її відсутність — за нею діють як за правдою.

Формат запису:

```markdown
## Токени валідуються в одному місці
**Де:** src/auth/verify.ts → verifyToken
**Чому:** було дві копії перевірки, розʼїхались після зміни TTL —
прод три дні пускав протерміновані токени.
**Не роби:** не додавай перевірку в middleware.
**PR:** #142
```

`Де` — якір. Окремого механізму інвалідації немає навмисно: агент, беручи запис
у роботу, все одно відкриває цей файл, і якщо символа немає — бачить це тоді,
коли це важить. Карта — підказка, ніколи не джерело правди.

## Правила надійності

- Помилка інструмента вертається в модель як `tool_result` з `is_error: true`,
  а не кидається вгору. Це найдешевша самокорекція.
- Помилка виклику моделі → `status: "failed"` плюс причина в `run.error`.
  Run ніколи не лишається в `running` назавжди.
- `maxSteps` обовʼязковий: крива модель інакше спалює бюджет мовчки.
- `save()` після кожного кроку, не в кінці.
- Untrusted input: усе з GitHub (README, тіла issues, коментарі) потрапляє в
  контекст загорнутим у `<untrusted source="...">…</untrusted>`.
- Ідемпотентність: маркер у тілі issue (`<!-- run:run_123 task:4 -->`) плюс запис
  зовнішнього id у власну таблицю до того, як результат віддається моделі.

## Команди

```bash
npm run typecheck                     # tsc --noEmit
npm run dev -- run "<задача>"         # створити run і працювати до паузи
npm run dev -- reply <id> "<текст>"   # продовжити run, що чекає на людину
npm run dev -- retry <id>             # повторити перерваний run
npm run dev -- show <id>              # стан run

npm run try-wire      # справжній HTTP-запит через локальний сервер-підміну
npm run try-storage   # 11 перевірок FileStorage
npm run try-tools     # 9 перевірок реєстру інструментів
npm run try-llm       # 7 перевірок підробленої моделі
npm run try-loop      # 13 перевірок циклу
```

Змінні оточення: `AGENT_LLM=demo` (офлайн-модель, без витрат), `MODEL`,
`MAX_STEPS`. Стан runs — у `.runs/`, поза git.

Для швидкої діагностики запиту: `ANTHROPIC_LOG=debug npm run ping` — вбудоване
логування SDK; глибше двох рівнів вкладеності воно згортає, тоді `try-wire`.
