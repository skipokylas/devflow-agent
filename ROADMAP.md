## Блокер

**Цільовий репозиторій для фаз 1–2 не обраний.** Потрібен форк реального
проєкту: 20k+ рядків, нетривіальна авторизація, довга історія з ревертами й
обговореннями, живий CI. Форк — бо агент має створювати там issues й PR.

Кандидати: `next-auth` (авторизація — сам домен), `cal.com` (великий моноріпо,
живий CI), `directus` (ролі й права). Або власний старий проєкт — найкращий
тест якості журналу, бо є еталон у голові.

Без цього фаза 1 не починається. Механіку (коміти, PR, ворота) можна тим часом
робити на `devflow-agent`.

## Наступний крок

1. **Обрати цільове репо** — блокер вище.
2. **Справжній ключ у `.env`** і перший прогін на моделі: чи вона взагалі кличе
   `read_file` за поточним системним промптом. Починати з `MODEL=claude-haiku-4-5`.
3. **Таблиця `events`** — виклики, токени, вартість. Якщо продукт нарівні з
   навчанням, юніт-економіка потрібна з фази 1, а не «колись».

## Відкриті питання

- **Цільове репо** — блокер, див. вище.
- **Кодинг делегуємо Claude Agent SDK чи Claude Code як підпроцесу** — рішення
  ще не приймали, я лише запропонував не писати свій.
- **Борд**: ClickUp / Trello / Linear. За портом `Board`, вибір відкладено.
- **Чат**: Telegram / WhatsApp. За портом `Channel`, вибір відкладено.
- **Формат зберігання плану** (фаза 3): у сховищі цілком одним JSON чи розбитий
  на задачі окремими рядками.
- **Межа run при моніторингу** (фаза 7): CI впав через годину після мержу — це
  продовження того самого run чи новий?
- **MCP**: власний сервер чи готовий GitHub MCP, і чи варто спершу зробити
  прямий REST для порівняння.

## Технічний борг

Нічого з цього поки не блокує.

- `agent list` немає — незавершений run знаходиться тільки за збереженим id.
  Саме тут файлове сховище впреться в межу й почнеться перехід на SQLite.
- Таблиці `events` немає: `messages` показує, що бачила модель, але не те, що
  насправді сталося (виклики, вартість, помилки). Переїжджає у фазу 1.
- Untrusted-обгортка не реалізована — знадобиться у фазі 1, щойно вміст файлів
  почне потрапляти в контекст.
- Модель дозволів — заглушка `approvedActions: new Set()`. Стає реальною
  вимогою у фазі 5, коли агент почне комітити.
- Резидентний воркер: теперішня схема «процес помирає на паузі» навчальна.
  Продукту потрібен процес, який слухає вебхук і викликає `resume`. Фаза 4.
- Компакція історії не потрібна на теперішніх обсягах; `maxSteps` — єдине, що
  зараз стримує ріст контексту.
- `try-*` — саморобні сценарії з `console.log`. vitest, коли зʼявиться CI.
- Якорі в журналі рішень без SHA й інвалідації — навмисно. Ускладнювати, тільки
  якщо агент справді спрацює за протухлим записом.
