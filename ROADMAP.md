## Наступний крок

Три варіанти, у порядку зростання витрат:

1. **`agent list`** — показати runs зі статусом `waiting_human`. Безкоштовно.
   Саме тут файлове сховище впреться в межу (перебір усієї теки замість
   `WHERE status = ?`), і почнеться перехід на SQLite.
2. **`agent chat`** — інтерактивна оболонка: `readline` навколо `advance`/`resume`,
   ядро не змінюється. ~40 рядків. Заодно нормальний рендер історії, щоб
   `[tool_use]` показувався як `→ читаю package.json`.
3. **Фаза 1** — справжній ключ у `.env` і перший прогін на моделі. Перевірити,
   чи вона взагалі кличе `read_file` за системним промптом із `cli.ts:19`.
   Починати з `MODEL=claude-haiku-4-5`.

## Відкриті питання

- **Конкретний репозиторій для роботи не обраний.** Фаза 1 потребує реального
  проєкту з нетривіальною авторизацією.
- **Формат зберігання плану** (фаза 2): у БД цілком одним JSON чи розбитий на
  задачі окремими рядками.
- **Власний MCP-сервер чи готовий GitHub MCP** (фаза 4) — і чи варто спершу
  зробити прямий REST для порівняння.
- **Межа run при моніторингу** (фаза 5): CI впав через годину після мержу — це
  продовження того самого run чи новий?

## Технічний борг

Записано в момент появи, щоб не забути. Нічого з цього поки не блокує.

- `agent list` немає — знайти незавершений run можна тільки за збереженим id.
- Таблиці `events` немає: `messages` показує, що бачила модель, але не те, що
  насправді сталося (виклики, вартість, помилки).
- Untrusted-обгортка ще не реалізована — знадобиться на фазі 1, щойно вміст
  файлів почне потрапляти в контекст.
- Компакція історії не потрібна на теперішніх обсягах, але `maxSteps` — єдине,
  що зараз стримує ріст контексту.
- `try-*` — саморобні сценарії з `console.log`. vitest додамо, коли перевірок
  стане більше або зʼявиться CI.
- Системний промпт (`cli.ts:19`) написаний навмання й не перевірявся на моделі.
