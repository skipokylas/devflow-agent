Агент написав і здав власну фічу: квиток #9 → аналіз коду → правки в робочій
копії → `typecheck` → PR #10 → мерж. `devflow serve` працює: список прогонів,
водоспад за посиланням, 400 на спробу виходу за межі, 404 на неіснуючий трейс.

Перший живий прогін із написанням коду (квиток #9, `devflow serve`) знайшов
чотири помилки інфраструктури, усі виправлені: дозволи не доходили до реєстру
інструментів; три окремі підтвердження замість одного; `maxSteps` 8 замалий і

що ворота якості провалювались би завжди.

Декомпозиція перевірена на живому квитку, не лише в сценаріях: задача
«Додати devflow serve» → аналіз коду → план із трьох підзадач → ворота
дозволу → «так» коментарем → issues #6, #7, #8 створені в `Backlog`.

Агент бере квиток із дошки GitHub Projects, аналізує репозиторій, відповідає з
посиланнями на файли, питає людину коментарем під issue, підхоплює відповідь,
звітує одним коментарем, який редагує по ходу, і кладе картку в `In review`.
Доопрацювання коментарем продовжує ту саму історію.

Команди: `auth · init · board · tick · watch · run · reply · retry · list ·
trace · serve · show`. Глобальна `devflow` після `npm link`, кілька репозиторіїв,
захист від змішування, живий показ у терміналі, трейси зі спанами й
HTML-водоспадом, 185 автоматичних перевірок.

**Жодної write-дії агент досі не робить.** `access: "write"`,
`approvedActions` і маркери ідемпотентності спроєктовані, але не використані
жодного разу — це і є суть наступної фази.

## Блокер

**Цільовий репозиторій для журналу рішень (фаза 2) не обраний.** Для фаз 3 і 5
підійде сам `devflow-agent` — він і задуманий як полігон механіки.

Для журналу потрібен форк реального проєкту: 20k+ рядків, нетривіальна
авторизація, довга історія з ревертами й обговореннями, живий CI. Форк — бо
агент має створювати там issues й PR.

Кандидати: `next-auth` (авторизація — сам домен), `cal.com` (великий моноріпо,
живий CI), `directus` (ролі й права). Або власний старий проєкт — найкращий
тест якості журналу, бо є еталон у голові.

Без цього не починається фаза 2. Фази 3 і 5 від нього не залежать.

## Відкриті питання

- **Цільове репо** — блокер, див. вище.
- **Коли вмикати `AgentSdkExecutor`** — рішення відкладено навмисно. v1 — власний
  цикл; поріг для другої реалізації: третина задач не проходить ворота з двох
  спроб. До того цифр немає, і вибір був би вгадуванням.
- ~~**Борд**~~ — обрано GitHub Issues + Projects. Порт `Board` закладений
  (`src/board/`), реалізація `GitHubBoard` — наступним кроком. GitLab і решта
  додаються тією ж структурою.
- **Чат**: Telegram / WhatsApp. За портом `Channel`, вибір відкладено.
- **Кілька процесів чи один із мультиплексуванням** для мультирепо — рішення
  фази 4, разом із воркером. Сьогодні достатньо не хардкодити репо як глобальний
  стан.
- **Формат зберігання плану** (фаза 3): у сховищі цілком одним JSON чи розбитий
  на задачі окремими рядками.
- **Межа run при моніторингу** (фаза 7): CI впав через годину після мержу — це
  продовження того самого run чи новий?
- **MCP**: власний сервер чи готовий GitHub MCP, і чи варто спершу зробити
  прямий REST для порівняння.
- **Підтримка OpenAI** — за портом `Llm`, внутрішній діалект лишається
  Anthropic. Вмикати за конкретною потребою: різниця в ціні, запасний варіант
  при недоступності, або вимога клієнта. Жодної з них поки немає, тому не
  робимо. Ціна питання — адаптер на 200–300 рядків, ядро не змінюється.
- **Промпт v3 перевірений лише на трьох питаннях без повторів.** Розширити набір
  і додати повтори, коли зʼявиться цільове репо: на ньому питання будуть
  складніші й дешева модель може посипатись.
- **Хмара для трейсів**: Amazon чи Google. На архітектуру не впливає — обидва це
  `PutObject` і підписаний URL. Вирішувати з появою першого платного користувача.

## Технічний борг

### Неузгодженість: порт і реалізація в одному файлі

`board/` і `forge/` тримають інтерфейс окремо від реалізацій, а `db/storage.ts`,
`trace/sink.ts` і `agent/llm.ts` — разом. Механічний рефакторинг, робити разом
із наступною правкою в цих файлах, а не окремим комітом.

### Вартість контексту

Прогін із декомпозицією коштував $0.1088 на найдешевшій моделі: 100 828 вхідних
токенів на 7 звернень. Кожен прочитаний файл лишається в історії й іде в модель
повторно на кожному наступному кроці — десять файлів дають квадратичний ріст.

Prompt caching увімкнено: на живому прогоні 51% вхідних токенів прийшли з кешу,
економія близько чверті. Кеш не вмикається на коротких запитах — мінімальний
префікс близько 4096 токенів, — тож виграш дає саме дороге.

Лишився другий важіль: читати діапазони рядків замість цілих файлів. Зараз
кожен `read_file` кладе в історію файл цілком, і він летить у модель повторно
на кожному наступному кроці.

### Ідентичність бота

Агент працює під особистим токеном, тому в GitHub його дії підписані твоїм
акаунтом. Два шляхи, обидва відкладені:

- **GitHub App** — правильний: коментарі від `devflow[bot]`, короткоживучий
  токен встановлення, обмежені права, працює для організацій. Ціна — обмін JWT
  на installation token і оновлення раз на годину.
- **Machine-акаунт** — дешевший: окремий обліковий запис і його PAT. Простіше,
  але зайняте місце співавтора в приватних репо й ще один акаунт.

Механіка від цього не залежить: свої коментарі пізнаються за маркером у тілі,
а не за автором.

### Планувальник — два покращення, відкладені свідомо

1. ~~Розбирати чергу до кінця в межах одного оберту~~ — зроблено.
2. **Опитувати дошку паралельно з роботою.** Цикл однопотоковий і чекає
   завершення `advance`, тому під час роботи нові квитки й відповіді людини не
   помічаються. Нові квитки все одно не почалися б раніше (робота послідовна),
   а от відповідь на питання чекає, поки агент звільниться. Складніше; робити
   тільки коли справді заважатиме.

Нічого з цього поки не блокує.

- `agent list` є, але робить перебір усієї теки з парсингом кожного файлу — саме
  тут файлове сховище впреться в межу й почнеться перехід на SQLite.
- Спанів немає: `messages` показує, що бачила модель, але не те, що насправді
  сталося (виклики, тривалість, вартість, помилки). Переїжджає у фазу 1.
- `LangfuseSink` — відкладено до появи цільового репо, коли прогони стануть
  щоденними і знадобляться агрегати по сотнях трейсів. Порт `TraceSink` уже
  стоїть, тож це друга реалізація на 50–80 рядків поруч із `FileSink`, не
  заміна. Перед підключенням вирішити: хмара чи self-hosted (docker з Postgres
  і ClickHouse), і закласти в схему спана поле «що можна показувати» — у
  трейсах лежить код репозиторію.
- `S3Sink` / `GcsSink` — коли зʼявиться перший платний користувач.
- Редагування секретів і термін зберігання трейсів — поле в схемі спана з
  першого дня; інакше при виїзді в хмару переписувати все накопичене.
- Untrusted-обгортка є для `read_file`; для тіл issues, коментарів і діфів —
  при підключенні GitHub.
- Модель дозволів — заглушка `approvedActions: new Set()`. Стає реальною
  вимогою у фазі 5, коли агент почне комітити.
- Резидентний воркер: теперішня схема «процес помирає на паузі» навчальна.
  Продукту потрібен процес, який слухає вебхук і викликає `resume`. Фаза 4.
- Мультирепо: репо визначається через `resolveRepo()` за remote URL, стан лежить
  у `~/.devflow/<slug>/`. Лишилось: `.devflow/config.yml` у цільовому репо
  (гілкова політика, ворота) і резидентний воркер.
- Компакція історії не потрібна на теперішніх обсягах; `maxSteps` — єдине, що
  зараз стримує ріст контексту.
- `try-*` — саморобні сценарії з `console.log`. vitest, коли зʼявиться CI.
- Якорі в журналі рішень без SHA й інвалідації — навмисно. Ускладнювати, тільки
  якщо агент справді спрацює за протухлим записом.
- Карта коду не потрібна, поки проєкт влазить у контекст. Зʼявиться разом із
  цільовим репо: кеш у `~/.devflow/<repo>/map/`, інкрементальне оновлення за
  `git diff`. Спільний обʼєктний кеш — коли над репо працює команда.
